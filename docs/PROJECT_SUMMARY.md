# HBnB Evolution — Project Summary

> Use this document as a prompt for a new chat to get full context on this project, or as reference for CV/interview preparation.

## What is this project?

HBnB Evolution is a full-stack Airbnb-like web platform built as the capstone project at Holberton School. It was developed across 4 incremental parts, starting from system design and ending with a working frontend connected to a production-ready REST API.

The project was built collaboratively and covers backend architecture, database design, authentication, role-based access control, and a dynamic frontend — all from scratch without frameworks like Django or React.

## Project Structure (4 Parts)

### Part 1 — System Design
- UML class diagrams for all entities (User, Place, Review, Amenity)
- Sequence diagrams for key flows (user registration, place creation, review submission, fetching places)
- API blueprint defining all endpoints before any code was written

### Part 2 — Backend v1 (In-Memory)
- Full REST API built with Flask and Flask-RESTX
- In-memory repository (dict-backed) implementing the Repository pattern
- Strict 3-layer facade architecture enforced from day one
- No authentication, no persistence — pure business logic validation

### Part 3 — Backend v2 (Production-Ready)
- Replaced in-memory storage with SQLAlchemy ORM
- SQLite for development, configurable for MySQL in production
- JWT authentication: login endpoint returns signed tokens
- Role-Based Access Control (RBAC): admins vs regular users with different permissions
- Entity relationships: one-to-many (Place→Review), many-to-many (Place↔Amenity via association table), cascade deletes
- SQL scripts for manual schema creation and initial data seeding
- ER diagram documenting the full database schema
- App Factory pattern (`create_app()`) for testable, configurable Flask instances

### Part 4 — Frontend
- Vanilla JS SPA consuming the Part 3 REST API via Fetch API
- JWT stored in cookies; protected sections shown/hidden based on auth state
- Dynamic place listing rendered from API response (no static HTML)
- Client-side price filtering without page reload
- 4 pages: Home, Login, Place Detail, Add Review

## Architecture

The backend enforces a strict 3-layer facade pattern:

```
Presentation  →  app/api/v1/       Flask-RESTX namespaces (HTTP in/out)
Business      →  app/services/     HBnBFacade — single entry point for all logic
Persistence   →  app/persistence/  Repository pattern (SQLAlchemyRepository)
```

**Rule:** API endpoints call only `HBnBFacade` methods. Models and repositories are never touched directly from the API layer. This makes the entire storage layer swappable without touching business logic.

## Notable Technical Decisions

**Why the Facade pattern?**
Keeps the API layer thin and testable. Swapping SQLAlchemy for another ORM (or going back to in-memory) requires changing only the repository, not the API or facade.

**Why JWT in cookies instead of localStorage?**
Cookies with `SameSite=Lax` offer basic CSRF protection. The token is sent automatically on every request without explicit headers in the frontend.

**Why Vanilla JS instead of React/Vue?**
The project requirement was to understand the DOM and Fetch API at the foundation level before using abstractions. Everything — rendering, state, routing — is done manually.

**Why SQLite for dev / MySQL for prod?**
SQLAlchemy's abstraction lets the same codebase run on both. The `DATABASE_URI` in `.env` is the only thing that changes between environments.

## Running the Project

```bash
# Backend (Part 3)
cd part3-backend
source venv/bin/activate
python3 run.py
# API at http://127.0.0.1:5000/api/v1/
# Swagger UI at http://127.0.0.1:5000/api/v1/

# Frontend (Part 4) — with backend running
cd part4-frontend
python3 -m http.server 8080
# Open http://localhost:8080

# Run tests
cd part3-backend
python3 -m pytest app/tests/ -v
```

Default admin credentials: `admin@hbnb.io` / `admin1234`
